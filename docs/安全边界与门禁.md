# 安全边界与门禁

一句话结论：**这套系统的安全现在靠"连不上"，不靠"有密码"；要给别人看，开端口与上锁必须同时做，缺一个就等于裸奔。**

本文写给"熟悉应用层校验、但不熟网络层"的读者。如果你平时想的是"参数格式对不对、用户存不存在、有没有权限"，那本文补的是另一层：**请求该不该到达这个进程**。

---

## 1. 威胁模型：我们防的不是黑客

这套系统不是银行，没有账号资产，所以不需要防"专门研究你、持续攻击"的对手。它面对的是三种现实场景：

1. **同网络里的好奇者**：宿舍、实验室、校园网，有人扫到你的 IP，打开浏览器看了一眼，随手点了两个按钮。
2. **你自己的一次误操作**：为了演示改了个端口，忘了另一件事。
3. **链接被转发出去**：你把地址发给一个人，他转给群里十个人。

这三种的共同点是：**对方不需要任何技术，只需要点按钮**。所以威胁不在"破解"，在"误触"。这决定了防御手段的形态——不是加密算法，而是**别让人连上，或者连上得先过一道口令**。

---

## 2. 危险面在副作用，不在读取

一般系统怕"数据被读走"。这套系统的风险清单不一样：

| 接口 | 方法 | 被陌生人点到会发生什么 | 可恢复性 |
|---|---|---|---|
| `/api/push/test` | POST | 用**你的** SMTP 账号真发一封邮件。反复点会让邮箱被风控限流，授权码可能失效 | 邮件撤不回；通道废了要重新申请授权码 |
| `/api/pipeline/run` | POST | 触发真实抓取；原话带频率时会**注册持久化定时任务**进 `bid_job` 表，之后每天自动抓取并发信 | 需逐条删除；已发出的信撤不回 |
| `/api/fingerprints/clear` | POST | 清空 67 条指纹。增量推送完全依赖指纹，清空后同一句话再跑，全部条目被当成"新增"，重复生成、重复推送 | **不可恢复**，无备份 |
| `/api/files` | GET | 批量下载你生成的所有招标 Word 汇总 | 不可撤销（已传输） |
| `/api/health` | GET | 明文返回发件邮箱地址、站点配置 | 信息泄露 |

一句话：**这里没有"只读就安全"的接口**。能点，就能产生真实后果。

## 3. 三层边界：网络层、传输层、应用层

后端开发者熟悉的校验几乎全在**应用层**，而这次出事的地方在**网络层**。三层各管一件事：

| 层 | 管什么 | 我们这套系统的现状 | 这层失效的后果 |
|---|---|---|---|
| 网络层 | 请求能不能到达进程（IP、端口、绑哪个网卡） | `127.0.0.1:80:80`，只绑回环 | 陌生人能打开页面，看到一切 |
| 传输层 | 传输是否加密、是否被中间人看见（TLS） | 无（纯 HTTP） | 口令、数据明文可嗅探 |
| 应用层 | 这个请求合不合法（参数、身份、权限、频率） | 基本没有（除 FastAPI 自动的 422 校验） | 参数错误、越权、重复触发 |

**关键认识**：应用层校验做得再全，也拦不住"有人点了不该点的按钮"。因为对他而言那些请求**完全合法**——参数正确、格式正确、类型正确。他就是一个合法用户，只是不该是用户。这类问题只能靠前两层解决。

反过来说，网络层隔离也不替代应用层校验。两层的关系是：**网络层决定"谁能进门"，应用层决定"进门之后能干什么"**。单人系统里，第一层做厚、第二层做薄，是合理的性价比。

---

## 4. 现状：安全来自"连不上"

`docker-compose.yml` 里写的是：

```yaml
ports:
  - "127.0.0.1:80:80"
```

这行的含义是：把容器的 80 端口，映射到**宿主机的回环地址**上的 80 端口。

- **回环地址（127.0.0.1 / localhost）**：操作系统内部的"自己跟自己通话"通道。发给它的包不会经过网卡，也不会离开这台机器。
- **网卡地址（10.16.47.167 之类）**：真正对外的门牌号。同网络的人只能通过它找到你。
- 所以绑定回环 = **门外没有人能敲到门**，Docker 的转发规则里根本没有一条指向网卡地址。

实测结论：`Test-NetConnection 10.16.47.167 -Port 80` 返回 False（连接被拒），而 `http://127.0.0.1/` 返回 200。这就是"本机能进、外面不能进"。

**必须看清的一点**：这份安全完全来自端口绑定，应用本身**一个鉴权都没有**。它是一个没锁的房间，只是门开在荒岛上。房间的锁从来没装过。

## 5. 只把端口改回 `80:80` 会怎样

`"80:80"` 让 Docker 在**所有网卡**上开门。于是 `http://10.16.47.167/` 对同网络的人直接可用，而应用里每个接口都还是原样——没有 token、没有 session、没有密码。

结果就是第 2 节那张表里的每一行，对陌生人全部可点。而且这些操作**不需要技巧**：打开页面、点一下"测试邮件"、点一下"执行全链路"，就完成了。

这也是为什么不能"先开放、回头再补认证"：中间态没有任何人盯着，却已经具备全部副作用能力。

---

## 6. 为什么"以为关着"比"确实开着"更危险

这句话的重点是**认知**，不是物理风险。

- 现在你确切知道：外面进不来。这个判断是真的，所以你会正确地行事——不会把地址发到群里，不会让机器裸着过夜。
- 如果改成了 `80:80` 却没上认证，你会以为自己"已经处理过安全问题了"。因为你**确实动过配置**，而"动配置"这件事在记忆里和"加固"是粘在一起的。
- 于是你会放心分享链接、放心让服务常开。风险从"不存在"变成"存在，且你不知道"。

更麻烦的是**这种错不报错**。页面正常、日志正常、定时任务正常，唯一异常出现在后果发生时：邮箱被封了，或者收件人收到一封你没写过的信。

工程上把这种现象叫**配置漂移**：你按心里的模型以为系统是 A 状态，实际是 B 状态，而两者之间没有任何机制提醒你。对策只有一条——**把两件事绑成一个原子动作**，见下。

---

## 7. 规矩：没装锁，就别开门

> 开端口 = 把门开到马路上。加认证 = 给门上装锁。这是同一个动作的两半，不能分成两次。

顺序上宁可**先装锁、再开门**：认证配置写好、`nginx -t` 通过、挂载到位，最后一步才改端口。这样任何一个中间时刻，最坏情况也只是"门没开"，而不是"门开了没锁"。

## 8. 三档方案，按暴露范围选

| 场景 | 做法 | 强度 | 局限 |
|---|---|---|---|
| 只自己用（当前） | 端口绑 `127.0.0.1` | 最强（网络层不通） | 无，但也无法远程访问 |
| 给同组/同宿舍看 | 端口改 `"80:80"` **＋ nginx Basic Auth** | 中 | 纯 HTTP 下口令明文，同网段可嗅探；口令会被分享、被遗忘 |
| 放公网给评委看 | Cloudflare Tunnel + Access（邮箱验证码），或云服务器 + 域名 + HTTPS | 高 | 需配置外部服务；国内绑域名要 ICP 备案 |

**顺序上的认识**：Basic Auth 是过渡工具，不是终态。它解决的问题是"挡住随手点两下的人"，解决不了"有人在同网段抓包"。真要对外，TLS 必须在链路里，口令才不是裸奔。

## 9. 启用 Basic Auth 的完整步骤

当前 `deploy/nginx.conf` 顶部有两行注释，默认关闭。启用需要四步一起完成：

1. 生成口令文件（首次会拉一个约 60MB 的 httpd 镜像，仅用于生成）：

```powershell
docker run --rm httpd:2.4-alpine htpasswd -nbB <用户名> <密码> > deploy/htpasswd
```

2. `docker-compose.yml` 的 nginx 端口改回 `"80:80"`。
3. nginx 服务 volumes 增加一行 `./htpasswd:/etc/nginx/htpasswd:ro`。
4. 取消 `nginx.conf` 里 `auth_basic` 与 `auth_basic_user_file` 两行注释，重建：

```powershell
docker compose -f deploy/docker-compose.yml up -d
```

`deploy/htpasswd` 已在 `.gitignore`（含口令哈希，不进公开仓库）。验证两件事：未带口令请求应返回 **401**，带对口令应返回 **200**。

## 10. 为什么不做用户系统

- 单人、单租户：没有"谁的数据归谁"的问题，账号体系的收益是零。
- 账号体系要付的成本：注册、密码重置、会话存储、找回流程、角色权限、审计——每一样都是新增攻击面，也都要维护。
- 真要对外展示，比登录更管用的是**演示模式**：在配置层禁用 `push`、`schedule`、`fingerprints/clear` 三个写操作，接口直接返回 403。评委看到完整界面与真实数据，但点不出任何副作用。

判断标准很简单：**问"第二个人需要独立的账号吗"。如果答案是不需要，就不要用户系统。**

## 11. 术语小抄（给不熟网络的人）

| 词 | 一句话解释 |
|---|---|
| 回环地址 | `127.0.0.1`，机器内部自己跟自己通话的地址，包不出网卡 |
| 网卡地址 | 如 `10.16.47.167`，对外真正的门牌号，同网络的人靠它找到你 |
| 端口 | 一台机器上区分不同服务的编号，80 是 HTTP 默认 |
| 端口映射 | 容器内部端口 ↔ 宿主机端口 的对应关系，Docker 负责转发 |
| 绑定地址 | 服务"只接受哪个网卡上的连接"。绑回环即外面不可达 |
| 反向代理 | 外部请求先到 nginx，再由 nginx 转给后端（本项目的 `/api/` → `app:8000`） |
| TLS / HTTPS | 给传输加密，中间人看不到内容；没有它，口令是明文 |
| 401 / 403 | 401 = 你没证明你是谁；403 = 证明了你，但不许做这件事 |
