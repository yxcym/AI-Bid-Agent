## 四、选型说明要点（下次展开成正式对比文档）

对比对象：原先只有 README 的纯文档项目（无代码、无运行时）。

1. 运行速度：纯文档零运行；本架构单进程 FastAPI + 线程池跑同步抓取，mock 全链路毫秒级，真实两站点一轮在十秒量级。原 Java+Redis+双服务方案要跨进程两次序列化、两次 HTTP 跳转，同样任务多出一次网络往返和一次容器/进程调度。
2. 开发效率：docstring 即类型约束，改站点只改 config.yaml 一个字段；Java 方案新增一个站点要动 DTO、Controller、Service、Mapper 四层。
3. 维护成本：去掉 Redis 和 Maven 两个外部依赖，SQLite 单文件可直接拷走；Java 方案需维护 Redis 实例、Quartz 建表脚本、双语言构建链。
4. 交付可信度：答辩时能当场跑一次增量推送，纯文档只能讲 PPT。
5. 迁移成本：核心是 Playwright 登录态，Python 是官方一等公民；Java 侧只能用非官方封装。

**A. 「至少1个登录站点」的口径更正**

仓库内该表述的唯一出处是 `docs/readme_old.md` 第28行（方案构想版 README，描述 Java＋Python 混合架构时的功能指标）。同一文件第44行"严格按赛题要求生成标准化 Word 文档"是全文唯一明确归因赛题的表述——即：来自赛题的地方标了归因，这句没标。组委会公开赛制规则的评审维度只有四条（AI创新性、业务价值、可推广性、方案专业度），不含登录态这类技术硬指标；具体企业命题任务书不在公开可查范围，也未存于本仓库（仓库内与赛事相关的实物仅参赛证明一张）。

结论：按"方案自设指标、可选增强"处理，不再作为合规缺口。真要做，只挑免费注册即可见列表的地方交易平台样本，不碰付费与需资质的站点；`needs_login` 明确报错的分支保持不动。

**B. 服务侧前台（匿名只读＋邀请口令＋全站额度上限）**

构想三层：

1. 匿名访客只读缓存——既有结果、趋势图、文档列表，不能触发新一轮抓取与模型调用（"隔玻璃看"）。
2. 受邀者凭一串口令使用，按日记次（一人一串、备注名、可吊销），超额拒绝并告知剩余次数（"发纸条"）。
3. 全站每日模型调用有总额上限，到顶自动退回规则解析、关闭摘要（"总闸"）。

不建完整用户系统：注册/找回密码/会话/角色对单人单租户项目是纯负担，"口令＋配额"一张表即可覆盖"给评委/同事开临时权限"的真实场景。成本依据：抓取不烧钱，LLM 才烧钱，故配额压在 LLM 解析与摘要上；计日逻辑可复用 `history.py` 的 Asia/Shanghai 处理。

**触发条件**：把服务地址发给本机以外的任何人之前（局域网评委访问或公网）。当前仅绑 127.0.0.1，风险为零，故暂不实现。

**C-1. 正文抽取落地（2026-11-28）**

- 做法：**只对"本轮新增"且"本轮要出文档"的条目补抓详情页**，增量语义天然控量；每站每轮上限 `detail_max_per_site`（当前 12）。
- 三层降级：站点 `detail_selector` 显式指定 → 常见命名（content/article/detail/mainbody/zoom/con-t）→ 文本密度评分 → body 兜底；选择器命中但不足 60 字视为失效，自动回落通用抽取。
- 已校准的选择器：`ccgp` = `div.vF_detail_main`（673 字，body 全文本 977 字含导航噪音）；`hefei_gc`/`hefei_cg` = `div.ewb-info-main`（273–612 字；外层 `div.container` 会带"打印/首页>交易信息"导航，不用）。
- 两个实测得来的清洗规则：①表格按 `<tr>` 聚合成"字段 值"一行（政府站大量用 table 排版，逐格换行会把 600 字吃成"地/址：/合肥…"碎片）；②只在块级标签断行，内联 span 连写（否则"名/称："被拆成两行）；③剔除 `[if !supportLists]` 这类 Word 域代码残渣与纯英文锚点行。
- 落点：`Notice.content` 仍受 `doc.max_chars_per_item`（600）约束，文档与摘要口径一致；`PipelineResult.detail_fetched` 暴露成功补抓条数（前端 KPI 显示"正文已补"）。
- 详情页请求策略：ccgp 虽列表页被 WAF 拦（403），但**详情页 httpx 直连 200**，故 playwright 站点也先走 http，全部失败才开一次浏览器批量兜底。
- 实测：2026-11-28 跑"储能 电站 招标"，抓 42 / 新增 36 / 正文补 26，Word 内条目正文从"长丰。""公开招标；合肥。"这类 3–8 字碎片变成 600 字带项目编号、资格要求、问答正文的段落。
- 已知边界：单轮每站只补前 12 条，超出部分仍用列表页摘要（`warnings` 会记"补全 N/M 条"）；~~关键词只取原话里的一个词，宽查询会带回不相关公告~~ **已于同日修正，见 C-2**。

**C-2. 检索取词修正（2026-11-28）**

- 现象："充电站 建设 招标"被解析成关键词「建设」，接口 200 但抓回一堆高标准农田、机场机库，`is_relevant` 过滤形同虚设（"建设"几乎每条公告都含）。
- 改法（`app/intent/rule_parser.py`）：候选词片段先 strip 尾部"的"、再剥尾部泛词（建设/工程/项目/采购/招标/投标/施工/安装/调试/服务/设备/货物/总承包/信息/公告/汇总/情况/相关/最近/最新/近期/目前/现在/有关/关于），从后往前取第一个"剥完仍有 ≥2 字"的片段。
- 整句只有泛词时**返回空**，由 `service.run()` 直接提示用户补主题，不再拿"公告"两个字去全网搜。
- 实测：`充电站 建设 招标`→充电站；`合肥高标准农田建设项目`→高标准农田；`储能电站项目招标`→储能电站；`最近1周的合肥服务器采购公告`→服务器；`帮我找一下最近的招标公告`→空（提示用户）。

**D. 已核实不成立的旧结论（2026-11-28 核查，勿再重复）**

定时任务"重启即丢"不成立。`app/schedule/store.py` 用同一 SQLite 库建 `bid_job` 表（job_id/query/cron 三列），`add()` 内存注册与落盘一步完成，`main.py` 启动时 `restore()` 逐条重放并打印“定时任务恢复=N”。2026-11-28 实测：落一条测试任务 → `docker compose restart app` → 日志 `定时任务恢复=1`、`GET /api/tasks` 任务仍在且 next_run 重算为次日 09:00 → 删除后表内为空。此前"不持久化"的说法源于早期内存态版本，属过期信息。
