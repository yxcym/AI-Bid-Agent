# 架构与选型对比说明

回答一个问题：**这套Python单体实现，相对「只有README的纯文档项目」（A）和「README设想的Java+Redis双服务方案」（B），好在哪？**

先立坐标系：**竞赛已于2026年结束，本文不是答辩材料**。当前目标只有一个——把README从纸上谈兵的空中楼阁变成能跑、能改、能演进的实例。已确认的路线是纯Python先跑通、后续按需转Python+Java混合（见第四节），所以B方案不是被否决的对象，而是被排期的演进目标。以下对比基于2026-11-27本机实测，其中环境事实已于同日复核更正。

## 一、对比对象

| 方案 | 说明 |
|---|---|
| A. 纯文档 | 原仓库状态：一份README，零代码、零运行时 |
| B. README设想栈 | Java 17＋Spring Boot＋LangChain4j＋Quartz＋Redis＋POI，外加Python/FastAPI/Playwright爬虫侧车，双服务。现为阶段2混合形态的预案，不是被否决的方案 |
| C. 当前实现 | Python 3.12单服务：FastAPI＋httpx/BeautifulSoup＋SQLite＋APScheduler＋python-docx |

## 二、五维对比

### 1. 可交付性：从0到1的差距

A方案的交付物是一份「计划」，B、C的交付物是能当场跑的系统。2026-11-27实测：C方案从冷启动到出第一份Word（`最近3个月的上海充电桩…_202611270555.docx`，37.5KB、32段落、含标题/检索条件/来源/日期/原文链接），全程约10秒。A方案无论讲多久，都变不出这份文件。**「空中楼阁」这个评价只有代码能撕掉——实例化的第一意义就在这里。**

### 2. 运行速度

- 首轮全链路（解析→抓10条→清洗→指纹去重→写Word→注册cron）：**秒级**（mock模式下毫秒级，真实HTTP模式预期十秒级两站点）
- 二轮增量（同句重跑）：fetched=10、fresh=0、**零文档产出**，指纹判定为O(1)的SQLite主键查询
- B方案同样任务要跨进程两次HTTP＋序列化（Java核心服务↔Python爬虫），再过一层Redis网络往返；每次任务调度都多两次网络跳转与两次进程切换。单机实例化与调试循环里，这些开销每一轮都在白付。

### 3. 开发效率

| 动作 | C方案（当前） | B方案（Java双栈） |
|---|---|---|
| 新增一个站点 | `config.yaml`加一段（约8行配置） | 爬虫侧车Python＋Java侧DTO/Service各一层 |
| 新增一个解析规则 | `rule_parser.py`加一行正则 | Java重编译＋Python侧同步修改 |
| 换文档样式 | `generator.py`一个类 | POI代码＋DTO字段联动 |

实测支撑：从搭骨架到全链路验证通过（含修2个bug），累计约一天；Java栈按苍穹外卖式分层惯例，同样的功能至少要写Controller/Service/Mapper/DTO四层外加跨服务契约。**vibe coding模式下AI产出与人工审查的往返次数，C方案约为B的三分之一**。

### 4. 维护成本

- **外部依赖数**：C＝0（SQLite随进程走、APScheduler内嵌）；B＝2（Redis实例＋Maven构建链），还要维护双语言、双进程的部署与日志
- **排障面**：C一条进程一条日志流；B要跨两个进程对时间戳。曾实测排查过一次：`帮我看一下`被误解析成关键词“看”，在C方案里是一条日志＋一处正则修复（15分钟）；同样的bug在B方案里要先定位它在Java侧还是Python侧
- **环境门槛**（2026-11-27复核更正）：本机事实是——Maven 3.9.5已装于`D:\WorkEnvironment\maven`（只是未进PATH，配JAVA_HOME即用）、Redis 7.4.2有现成安装包与服务脚本（`D:\WorkEnvironment\redis`），真正缺的只有Docker运行时。B方案的真实成本不在「补环境半天」，而在**日常**：每次改动要同时维护Maven构建链与pip依赖两套，调试要跨Java/Python两进程对日志。C方案`run.ps1`一条命令、一条日志流

### 5. 迁移与扩展成本

这个项目的终极形态是Agent，核心难点按重要性排序：

1. **登录态抓取**——Playwright官方只有Python/Node/Java三套API，其中Python是文档、社区、示例最全的一等公民；Java侧只有非官方封装（playwright-java官方有，但爬虫生态如反爬对抗、代理池、验证码识别几乎全在Python侧）
2. **LLM清洗与解析**——后续接模型时，Python生态（langchain、openai sdk、评测工具链）是原生产业；LangChain4j是追赶者
3. **文档生成**——python-docx约100行出正式版式；POI同等效果代码量约翻倍

也就是说：**越是往深水区（真实站点、登录态、LLM）走，Python侧的现成供给越多；Java的优势（强类型、企业级工程规范）不会消失，但属于后期——这正是第四节把它排进阶段2而不是起步的原因**。

## 三、对A方案（纯文档）的直接回答

纯文档的价值是选题与架构预案——这它已经完成了（README里的四模块划分、痛点分析被C方案全盘继承）。但它遗留三个只有写代码才能解决的问题：认为Java双栈更“工业级”（对起步阶段是负债，对后期混合演进是预案——见第四节）、认为运行细节可以后补（选择器、指纹策略、增量语义全是写代码时才暴露的真问题，例如`帮我看一下`这种输入在纸面上永远想不到）、认为讲清楚架构就算完成（实例化的验收标准是`fresh=0`当场出现，不是文档页数）。

**结论：C方案不是对A方案的否定，而是把A方案从「构想」变成「可运行实例」的第一步。当前走Python是用户确认的路线——本项目的技术重心（登录态爬虫＋LLM）在Python主场，先跑通再演进；Java没有被否决，而是被排期。**

## 四、阶段路线：Python先行，Java按需后置

竞赛结束后的目标已确认为**实例化**，分三阶段：

| 阶段 | 内容 | 状态 |
|---|---|---|
| 0. 纯Python全栈跑通 | 四模块＋前端＋mock链路，增量语义可验证 | 已完成（待真实站点校准） |
| 1. 实例化深化 | 真实站点抓取、Playwright登录态侧车、LLM解析与清洗接入 | 待启动 |
| 2. Python+Java混合 | Java承接意图解析与调度引擎（Spring Boot＋Quartz，对齐原README设想，也是你的Java深化主线）与企业级POI文档规范；Python保留采集侧车与LLM生态 | 用户意向，触发条件见下 |

**阶段2的触发条件**：阶段1稳定运行后，结合Spring Boot学习主线（苍穹外卖之后的下一个实战项目）启动。此时双服务不是起点包袱，而是实例化完成后的架构演进——原B方案的Redis（接手指纹存储）与Quartz（补掉「重启丢任务」边界）在该阶段顺势归位。

**为什么混合可行**：四模块边界清晰、`/api`契约稳定。把某个模块整体迁去Java时，Python侧把对应Protocol实现换成HTTP客户端即可，编排层（`pipeline/service.py`）一行不改。

## 五、留了哪些回头路（不是一条道走到黑）

- `intent/base.py`、`crawler/base.py`都是Protocol接口：换LLM解析器、换Playwright抓取器，调用方零改动
- `crawler.mock`开关：校准真实站点前，演示不依赖外网
- `intent.parser: llm`＋三个环境变量：模型随时可插拔，失败自动回退规则解析
- SQLite指纹表结构简单，未来换Redis只需要重写`SqliteFingerprintStore`的三个方法（阶段2顺势执行）
