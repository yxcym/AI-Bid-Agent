## 2026-11-27 第二十一轮：hybrid 意图解析落地——阶段1②完成（差一个 key）

**做了什么**

- **config.py**：新增 `LlmSection`（api_key/base_url/model/timeout，OpenAI 兼容协议，默认 DeepSeek）；`IntentSection` 加 `llm` 子段；环境变量通道 `BIDAGENT_LLM_API_KEY/BASE_URL/MODEL`（优先级最高，容器场景用）；`llm_credential_source()` 供启动日志，不打印具体值
- **llm_parser.py 重写**：①接受 `LlmSection` 注入（不再只读环境变量）；②**prompt 注入当天日期**——修掉"模型按训练数据年份猜相对时间"的硬伤；③**prompt 注入可用站点清单**——模型判定 sites 有了依据；④JSON 解析失败自动带"只输出 JSON"指令重试一次，网络错误仍直接抛给上层
- **hybrid_parser.py 新增**：规则先行，两类保守升级信号——keyword 缺失/垃圾（"天亮就给我推一份"这类动词短语被规则误当关键词）、疑似频率词但 cron 未解出（"用户以为挂上了定时"的静默事故源头）；模型只填空位/垃圾位，规则干净值一律不动；模型任何失败整体降级纯规则并标 `rule-only`
- **main.py 装配**：`parser: hybrid` 分支；无 key 时返回 `hybrid(no-llm)`（health 可见配置意图，等效 rule）
- **tests/ 目录首次入库**：`test_intent_llm.py` 14 用例全 mock（围栏/客套话 JSON、prompt 含今天日期与站点、重试一次、四类 hybrid 语义、降级标记、no-llm 命名），全过
- config.yaml 注释改写并置 `parser: hybrid`（无 key 自动等效 rule，切换无风险）；`secrets.yaml.example` 补 `intent.llm` 段与三家 provider 填法；requirements 加 pytest 注释行（开发依赖不进镜像）

**关键决策**

- **hybrid 而非全局 llm**：`最近3个月的合肥充电桩招标信息` 规则百发百中，没必要为它花一次调用、引一次随机性；只有口语句才升级。调用量趋近于零，免费额度足够——这是"不想花钱"约束下的解
- **不用 Ollama**：本地 7B 吃数 GB 内存且 cron 偶尔错；云端 key + hybrid 的成本趋近于零，内存占用为零
- **升级信号保守且可叠加**：多升级一次只是几厘钱，漏升级是"定时静默没挂上"的真事故；信号词表偏宽（含"一份/就给我/天亮"等）
- **垃圾关键词也触发升级**：实测发现规则会把"天亮就给我推一份"当 keyword——不升级的话模型补不了（合并策略只填空位），所以垃圾词按缺失处理，允许模型覆盖
- **docker 重建而非仅重启**：代码进了镜像，必须 `--build`；顺手验证了引擎意外停止后容器随引擎自动恢复（unless-stopped）

**验证结果**

- 14/14 单测过；全应用导入 + 装配冒烟通过（`parser=hybrid`、`hybrid name=hybrid(no-llm)`）
- 容器重建后 health：`parser=hybrid(no-llm) fp=67 push=true jobs=0`
- 三句话对比（无 key，全走规则）：标准句 kw=充电桩/region=合肥 干净；两句口语 kw 分别为"天亮就给我推一份""发我"——正是 key 到位后会升级给模型补的形态
- 期间 Docker 引擎意外停止过一次（管道消失、容器全停），`docker desktop start` 后容器自动回来——自启链路经受了一次真实故障演练

**遗留问题**

- **key 未配置**：等用户确定 provider 并把 key 写入 secrets.yaml（或环境变量），写入后 `up -d --build` 一次即生效
- 真实调用尚未发生：prompt 效果、DeepSeek 对 cron 的正确率、延迟表现都待真跑一轮验证（用三句话对比法）
- tests 目录只有 intent 一个文件，rule_parser 的历史用例（第十六轮的 8 例）还在会话里没入库

**下一步**

- 用户提供 key → 真跑 hybrid 三句话对比 → 把 rule_parser 历史用例补进 tests/
- 之后是打包分发（PyInstaller）或按用户新需求走

## 2026-11-27 第十九轮：收窄暴露面——端口绑回环，门禁方案定型

**做了什么**

- 实测暴露面：nginx 原 `"80:80"` 使端口监听在 `::`（所有网卡），防火墙中 `Docker Desktop Backend` 两条规则为 Allow/Public，本机处于校园网（`10.16.47.x`）——即同一网络内任何人都能打开面板，而**全站零鉴权**
- 把 `docker-compose.yml` 的 nginx 端口改为 `"127.0.0.1:80:80"`，只映射回环地址
- 在 `deploy/nginx.conf` 顶部写好 Basic Auth 的启用说明与两行配置（默认注释）：生成口令文件 → 挂端口 → 挂载 → 取消注释，四步齐全
- `.gitignore` 新增 `deploy/htpasswd`（口令哈希不进仓库）
- `docs/操作指南.md` 增加"访问范围与门禁"小节，写明"放宽到局域网必须端口与 Basic Auth 同时做"

**关键决策**

- **不做用户系统，只做门禁**。单人单租户系统没有归属问题，账号体系带来注册/重置/会话/角色全是新增攻击面与维护负担；真要给评委演示，"演示模式"（禁用三个写接口）比登录有用
- **门禁手段选 nginx Basic Auth** 而不是在 FastAPI 加 token：一层挡住整个站点（含静态与 `/api/`），后端一行不改，将来加 TLS 也在同一层
- **默认绑回环而非默认加密码**：当前唯一使用者就在本机，绑回环比设口令更彻底（口令会被分享、会被忘），且零配置成本
- 判断依据是"危险面在副作用不在读取"：`push/test` 可冒用邮箱发信、`pipeline/run` 可注册定时任务持续发信、`fingerprints/clear` 可清空 67 条指纹、`files` 可批量下载文档。这些没有一个是"读"，全是"做"

**验证结果**

- 本机 `http://127.0.0.1/` 返回 200，`/api/health` 为 `fp=67 push=true jobs=0`——功能未受绑定收窄影响
- 局域网侧 `Test-NetConnection 10.16.47.167:80` 与 `172.30.238.142:80` 均返回 False（连接被拒）
- `nginx -t` 通过：`syntax is ok / test is successful`（注释状态的 Basic Auth 段不影响加载）
- 前一轮的日志提交曾因 GitHub 通道中断连续失败，后台每分钟重试第 3 次成功落地（`4750201`）

**遗留问题**

- 演示模式（只读开关）尚未实现，仍是设想；要给评委开放时需补
- Basic Auth 段处于注释状态，未做一次真实启用的联调（口令文件生成、挂载、401/200 两条路径）

## 2026-11-27 第十八轮：切换为 Docker 唯一入口——交付形态收口

**做了什么**

- 卸载两个计划任务（`service\unregister.ps1`）×`schtasks /Query` 复查为空，停掉宿主 8000 常驻进程，消除"两套调度器共用 `data/bidagent.db`"的隐患
- 让 Docker Desktop 随登录自启：`docker desktop` CLI 无对应开关（`enable` 只暴露 `model-runner`），改 `%APPDATA%\Docker\settings-store.json` 的 `AutoStart: false → true`。**关键操作顺序**：先 `docker desktop stop` 再改文件再 `start`，避免桌面退出时把内存里的旧设置回写覆盖
- 文档口径整体翻转：`README.md` 快速开始改为 Docker 三条命令、`run.ps1` 降级为"无 Docker 的备选"；`docs/操作指南.md` 第 1 节重排编号——方式一 Docker（默认）、方式二双击 bat、方式三 `run.ps1`、方式四地址栏速启、方式五服务化常驻（标注"当前未启用"并写明退回步骤）；演示章节入口改为 80 端口
- 删掉操作指南里重复的旧"方式五 Docker"整块（上轮新增时与原方式四并存，编号已冲突）

**关键决策**

- **容器而非计划任务作为常态**：容器把 nginx＋app＋依赖一次性固化，换机器只差一个 `up`；计划任务依赖用户登录会话、脚本要处理 BOM/执行策略这类 Windows 特有坑，维护面更大
- **自启交给 Docker Desktop 自身**，不再自建第三个计划任务去"等引擎就绪再拉容器"。理由：`restart: unless-stopped` 已覆盖引擎重启后的容器恢复，重复造一个轮询器只会多一处要维护的故障点
- 保留 `service/` 四脚本不删：它仍是**无 Docker 环境**（评阅机、临时机器）的可用路径，文档已写明切换顺序（先 `docker compose down` 再 `register.ps1`）

**计划变更记录：本来怎么打算的，为什么改成 Docker 唯一入口**

第十六、十七两轮结束时的口径是**分层并存**：第一层服务化常驻（本机日常）→ 第二层 Docker（交付/上云形态，只在需要时 up 一下验证）→ 第三层打包分发。当时写得很明确——"本机就是工作站，宿主常驻启动快、调试直接，容器化不作为本机常态"。这个判断背后有一个**没写出来的假设**：两层可以同时存在。

第十七轮实测把这个假设撞碎了，原因是结构性的，不是配置疏忽：

- `docker-compose.yml` 把 `../data` 挂进容器，两种形态**共用同一个 `data/bidagent.db`**，而 `bid_job` 表只有一份
- `app/main.py` 启动时 `scheduler.restore()` 会重放表里的任务——宿主恢复一遍、容器再恢复一遍，同一个 cron 就成了两套调度器各跑一次：抓取两次、Word 两份、邮件两封
- 便宜的修法都不成立：加互斥锁要改 schema、给容器单独 db 就丢掉共享的指纹库（那 67 条指纹正是增量推送的基础）
- 于是"并存"只能退化为"互斥 + 每次人工切换"，而**这个失败模式是静默的**——邮件照常发，只是发两封，不报错、不告警，比直接崩掉更危险。靠人记得"切之前先停另一侧"，等于把正确性押在记性上

推翻原计划的第二根稻草是**不确定性消失**：第十七轮把三件套从"未在本机验证"打成全链路实测（构建、80 端口、真实抓取、Word 落盘、定时任务跨容器重建恢复）。原先不让容器当主入口，很大程度是"没验过、怕挂"；验过之后这条顾虑反而成了支持理由。

第三是维护面的算术。宿主常驻这条线上要照看六处：两个计划任务、XML 注册、UTF-8 BOM 坑、ExecutionTimeLimit 坑、看门狗脚本、PowerShell 5.1 与 7 双兼容。容器这条线上只有两处：一个 compose 文件、`restart: unless-stopped`。自启也只需 Docker Desktop 一个 `AutoStart` 开关，不必再造第三个轮询任务去"等引擎就绪再拉容器"。

第四是迁移性。容器换机器只差一条 `up`；宿主常驻换机器要重注册任务、重设执行策略、重装依赖——在"交付给别人"这个语境下几乎不可复用。

**明确接受的代价**：冷启动到可访问约十几秒（宿主常驻约 2–3 秒）；依赖 Docker Desktop 的 GUI 进程与用户登录会话，仍不是无人值守；镜像层落在 WSL 分发里，D 盘体积随镜像增长，需要定期 `docker system prune`。这三条与"能交到别人手上"相比，权重更低。

**结论**：不是推翻"交付形态分层"的思路，而是承认**分层必须互斥**，并在互斥的前提下选了可分发、可迁移的那一个。原计划没有作废，只是降级为备选——`service/` 四脚本保留，退回顺序写进操作指南。触发这次变更的直接指令来自用户拍板"换成 docker"。

**验证结果**

- 卸载后 `schtasks /Query` 两个任务均返回空；宿主 8000 已无监听
- 自启设置：`docker desktop stop` → 写 `AutoStart=true` → `docker desktop start` → 引擎 `server=29.9.3` 就绪；复查 `AutoStart=true` **未被回写覆盖**；`HKCU\...\Run` 存在 `Docker Desktop -> <Docker 安装目录>\Docker Desktop.exe`，`StartupApproved\Run` 中该项状态为启用
- **容器随引擎自启回来**：桌面重启后 `deploy-app-1`、`deploy-nginx-1` 均自动 Up（`RestartPolicy=unless-stopped` 已核），页面 `http://127.0.0.1/` 返回 200，`/api/health` 为 `fp=67 push=true jobs=0`
- 设置文件已留备份 `settings-store.json.bak`（同目录），改动可回滚

**遗留问题**

- Docker Desktop 登录自启只在"用户登录后"触发，仍不是无人值守；真正的服务器场景应换 Linux＋systemd 或云容器平台
- 引擎冷启动到可访问约十几秒，这段时间打开浏览器会连接失败，属预期，文档已说明
- 镜像仍未打版本标签/未试 `docker save`；打包分发（PyInstaller）与 LLM 意图解析仍未动

**下一步**

- 交付形态第三层：PyInstaller 单包分发，覆盖"连 Docker 都没有"的机器
- 或先补 LLM 意图解析，把 `parser: rule → llm` 打通

## 2026-11-27 第十七轮：Docker 三件套实测——交付形态升级第二层

**做了什么**

- **Docker 环境落地**：Docker Desktop 安装目录与数据位置迁到 D 盘（`<Docker 安装目录>`），Linux 引擎就绪（server 29.9.3 / compose v5.7.1）；基础镜像经国内源 `docker.m.daocloud.io` 拉取后 `docker tag` 回官方名（`python:3.12-slim` 179MB、`nginx:alpine` 103MB），Dockerfile 无需改动
- **堵掉一个真实的凭据泄露口**：原 `deploy/Dockerfile` 的 `COPY config ./config` 把 `config/secrets.yaml` **烤进了镜像**——镜像导出、推仓库、发给别人都等于交出发件授权码。新增根目录`.dockerignore`（排除`config/secrets.yaml`、`.venv`、`data/`、`output/`、`.git`、`node_modules` 等），`docker-compose.yml` 改为运行时只读卷挂入 `../config/secrets.yaml:/srv/bidagent/config/secrets.yaml:ro`
- **三件套全链路实测**（此前三个文件一直标着"未在本机验证"）：构建 → 起容器 → nginx 80 托管前端 → `/api/` 反代 → 真实站点抓取 → Word 落盘 → 定时任务跨容器重建恢复 → 拆除并恢复宿主常驻

**关键决策**
