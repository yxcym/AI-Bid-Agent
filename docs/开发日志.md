## 2026-11-28 第三十六轮：检索取词修正＋exe/离线包重打 v1.3.0（两笔账合掉）

**做了什么**

- **检索精度**：`rule_parser._extract_keyword` 重写——候选片段先 strip 尾部"的"、再剥尾部泛词（建设/工程/项目/采购/招标/投标/施工/安装/调试/服务/设备/货物/总承包/信息/公告/汇总/情况/相关/最近/最新/近期/目前/现在/有关/关于），从后往前取第一个剥完仍有 ≥2 字的片段；整句只有泛词时返回空，由 `service.run()` 提示用户补主题，不再拿"公告"去全网搜
- **版本号单点维护**：`app/__init__.py` 增 `__version__ = "1.3.0"`，`main.py` 的 FastAPI version 与 `/api/health` 的 `version` 字段都引用它（此前写死 1.0.0，分发物无法自证版本）
- **exe 重打**：`AI-Bid-Agent.spec` 打包 → `dist/AI-Bid-Agent.exe` 61.7MB（v1.1.0 为 20.9MB，主要增量是前端 echarts 与新增依赖）
- **离线镜像包重打**：`docker save deploy-app:latest nginx:alpine` → 594.6MB tar → 7z gzip → `release/ai-bid-agent-images.tar.gz` 590.1MB（含正文抽取后的镜像）

**关键决策**

- **泛词是"尾部"问题，不是"包含"问题**：`充电桩采购` 该留"充电桩"，而 `高标准农田建设` 该留"高标准农田"，所以对每段做尾部剥离而不是整段黑名单
- **全泛词宁可报错不硬搜**：返回空 → 上层提示"没识别出检索主题"，比搜回 60 条不相关公告体面
- **版本号只维护一处**：避免代码/文档/Release 三处漂移，health 可直接读
- **离线包不重打不行**：镜像重建后 Release 里的旧包会让人 load 到没有正文抽取的版本，属于"看起来更新了其实没有"的隐性坑
- **7z 不能在已有 .gz 上追加**：`a -tgzip` 对已存在的 gzip 会报 System ERROR（gzip 不支持多成员追加）；正确做法是先挪走/删除再压

**验证结果**

- 取词实测：`充电站 建设 招标`→充电站、`合肥高标准农田建设项目`→高标准农田、`储能电站项目招标`→储能电站、`最近1周的合肥服务器采购公告`→服务器、`帮我找一下最近的招标公告`→空

- `pytest` 104 passed

**遗留问题**

## 2026-11-27 第三十轮：钉钉通道联调修复（httpx query 覆盖坑＋双重编码）

**做了什么**

- 用户填入钉钉 webhook 后首发自测报 `code=40035 缺少参数 access_token`。排查：地址本身完整（token 64 位），真因是 **httpx 的 `params` 参数会覆盖 URL 原有 query**——`post(url?access_token=x, params={timestamp,sign})` 发出去只剩 timestamp/sign（`httpx.Request` 实测复现）
- 修复：新增 `merge_query()` 手动合并 query（parse_qsl 解析原 query → update → urlencode），`send()` 改为发合并后的完整 URL
- 该修复的测试暴露第二个问题：**签名被双重 URL 编码**（`dingtalk_sign` 先 quote_plus、`urlencode` 再编一次，`%2B` 变 `%252B`）。修正为 `dingtalk_sign` 返回原始 base64，URL 编码只在 merge_query 做一次
- secrets.yaml 事故处理：用户粘贴钉钉段时新建了 `push:` 顶层键，把原文件 `push.email` 段整个覆盖（YAML 重复键后者胜），**邮件 SMTP 授权码丢失**。程序化恢复结构（dingtalk/intent 原样保留，email 段补回 username/to_addrs，password 留空待用户重填）
- 测试补强：merge_query 保留 access_token、空 query 不变、send 发出的 URL 同时含 access_token 与签名、签名单次编码（`%25` 不得出现）

**关键决策**

- 「sign 函数返回原始 base64、编码归拼 URL 的层」——分层后每层职责单一，向量的测试语义也更干净
- 钉钉自测 errcode=0 通过但签名曾双重编码，推断用户机器人实际是**关键词校验**模式（消息标题固定含 `AI-Bid-Agent`，恰好像是关键词命中）；加签路径也一并修对，两种模式都正确

**验证结果**

- `pytest tests -q`：**72 passed**（新增 merge_query 回归 3 条＋签名向量改口径）
- 容器重建后两次真实自测：`已发送：群机器人→钉钉群`（用户群收到测试消息）
- health：`钉钉群 ready=true signed=true`；邮件段结构已恢复但授权码为空 → 显示缺凭据，待用户重填

- 邮件授权码需用户重填（原值随覆盖丢失，无处找回；126 邮箱可重新生成）
- 需与用户确认钉钉机器人安全设置模式：关键词模式则关键词须包含 `AI-Bid-Agent`；加签模式现已正确支持

## 2026-11-27 第十八轮：切换为 Docker 唯一入口——交付形态收口

**做了什么**

- 卸载两个计划任务（`service\unregister.ps1`）×`schtasks /Query` 复查为空，停掉宿主 8000 常驻进程，消除"两套调度器共用 `data/bidagent.db`"的隐患
- 让 Docker Desktop 随登录自启：`docker desktop` CLI 无对应开关（`enable` 只暴露 `model-runner`），改 `%APPDATA%\Docker\settings-store.json` 的 `AutoStart: false → true`。**关键操作顺序**：先 `docker desktop stop` 再改文件再 `start`，避免桌面退出时把内存里的旧设置回写覆盖
- 文档口径整体翻转：`README.md` 快速开始改为 Docker 三条命令、`run.ps1` 降级为"无 Docker 的备选"；`docs/操作指南.md` 第 1 节重排编号——方式一 Docker（默认）、方式二双击 bat、方式三 `run.ps1`、方式四地址栏速启、方式五服务化常驻（标注"当前未启用"并写明退回步骤）；演示章节入口改为 80 端口
- 删掉操作指南里重复的旧"方式五 Docker"整块（上轮新增时与原方式四并存，编号已冲突）

**关键决策**

- **容器而非计划任务作为常态**：容器把 nginx＋app＋依赖一次性固化，换机器只差一个 `up`；计划任务依赖用户登录会话、脚本要处理 BOM/执行策略这类 Windows 特有坑，维护面更大
- **自启交给 Docker Desktop 自身**，不再自建第三个计划任务去"等引擎就绪再拉容器"。理由：`restart: unless-stopped` 已覆盖引擎重启后的容器恢复，重复造一个轮询器只会多一处要维护的故障点
- 保留 `service/` 四脚本不删：它仍是**无 Docker 环境**（评阅机、临时机器）的可用路径，文档已写明切换顺序（先 `docker compose down` 再 `register.ps1`）

**计划变更记录：本来怎么打算的，为什么改成 Docker 唯一入口**

第十六、十七两轮结束时的口径是**分层并存**：第一层服务化常驻（本机日常）→ 第二层 Docker（交付/上云形态，只在需要时 up 一下验证）→ 第三层打包分发。当时写得很明确——"本机就是工作站，宿主常驻启动快、调试直接，容器化不作为本机常态"。这个判断背后有一个**没写出来的假设**：两层可以同时存在。

第十七轮实测把这个假设撞碎了，原因是结构性的，不是配置疏忽：

- `docker-compose.yml` 把 `../data` 挂进容器，两种形态**共用同一个 `data/bidagent.db`**，而 `bid_job` 表只有一份
- `app/main.py` 启动时 `scheduler.restore()` 会重放表里的任务——宿主恢复一遍、容器再恢复一遍，同一个 cron 就成了两套调度器各跑一次：抓取两次、Word 两份、邮件两封
- 便宜的修法都不成立：加互斥锁要改 schema、给容器单独 db 就丢掉共享的指纹库（那 67 条指纹正是增量推送的基础）
- 于是"并存"只能退化为"互斥 + 每次人工切换"，而**这个失败模式是静默的**——邮件照常发，只是发两封，不报错、不告警，比直接崩掉更危险。靠人记得"切之前先停另一侧"，等于把正确性押在记性上

推翻原计划的第二根稻草是**不确定性消失**：第十七轮把三件套从"未在本机验证"打成全链路实测（构建、80 端口、真实抓取、Word 落盘、定时任务跨容器重建恢复）。原先不让容器当主入口，很大程度是"没验过、怕挂"；验过之后这条顾虑反而成了支持理由。

第三是维护面的算术。宿主常驻这条线上要照看六处：两个计划任务、XML 注册、UTF-8 BOM 坑、ExecutionTimeLimit 坑、看门狗脚本、PowerShell 5.1 与 7 双兼容。容器这条线上只有两处：一个 compose 文件、`restart: unless-stopped`。自启也只需 Docker Desktop 一个 `AutoStart` 开关，不必再造第三个轮询任务去"等引擎就绪再拉容器"。

第四是迁移性。容器换机器只差一条 `up`；宿主常驻换机器要重注册任务、重设执行策略、重装依赖——在"交付给别人"这个语境下几乎不可复用。

**明确接受的代价**：冷启动到可访问约十几秒（宿主常驻约 2–3 秒）；依赖 Docker Desktop 的 GUI 进程与用户登录会话，仍不是无人值守；镜像层落在 WSL 分发里，D 盘体积随镜像增长，需要定期 `docker system prune`。这三条与"能交到别人手上"相比，权重更低。

**结论**：不是推翻"交付形态分层"的思路，而是承认**分层必须互斥**，并在互斥的前提下选了可分发、可迁移的那一个。原计划没有作废，只是降级为备选——`service/` 四脚本保留，退回顺序写进操作指南。触发这次变更的直接指令来自用户拍板"换成 docker"。

**验证结果**

- 卸载后 `schtasks /Query` 两个任务均返回空；宿主 8000 已无监听
- 自启设置：`docker desktop stop` → 写 `AutoStart=true` → `docker desktop start` → 引擎 `server=29.9.3` 就绪；复查 `AutoStart=true` **未被回写覆盖**；`HKCU\...\Run` 存在 `Docker Desktop -> <Docker 安装目录>\Docker Desktop.exe`，`StartupApproved\Run` 中该项状态为启用
- **容器随引擎自启回来**：桌面重启后 `deploy-app-1`、`deploy-nginx-1` 均自动 Up（`RestartPolicy=unless-stopped` 已核），页面 `http://127.0.0.1/` 返回 200，`/api/health` 为 `fp=67 push=true jobs=0`
- 设置文件已留备份 `settings-store.json.bak`（同目录），改动可回滚

**遗留问题**

- Docker Desktop 登录自启只在"用户登录后"触发，仍不是无人值守；真正的服务器场景应换 Linux＋systemd 或云容器平台
- 引擎冷启动到可访问约十几秒，这段时间打开浏览器会连接失败，属预期，文档已说明
- 镜像仍未打版本标签/未试 `docker save`；打包分发（PyInstaller）与 LLM 意图解析仍未动

**下一步**

- 交付形态第三层：PyInstaller 单包分发，覆盖"连 Docker 都没有"的机器
- 或先补 LLM 意图解析，把 `parser: rule → llm` 打通

## 2026-11-27 第十六轮：服务化常驻＋定时任务持久化——交付形态升级第一层

**做了什么**

- **服务化三件套**（`service/` 目录）：
  - `register.ps1` / `unregister.ps1`：注册/卸载两个计划任务（当前用户上下文，无需管理员）——`AI-Bid-Agent`（登录自启、隐藏窗口）＋`AI-Bid-Agent-Watchdog`（每 5 分钟检查端口，不在就拉起）

  - `watchdog.ps1`：看门狗，覆盖崩溃/误杀/自启失败一切"端口没人听"的情况
  - 计划任务用 XML 注册而非 schtasks 参数行，关键原因：schtasks 默认 ExecutionTimeLimit=3 天，常驻服务会被掐死，XML 里显式 `PT0S` 取消限制
- **定时任务持久化**：新增 `app/schedule/store.py`（`bid_job` 表：job_id/query/cron 三列，复用现有 SQLite 零新依赖）；`scheduler.add()` 内存注册＋落盘一步完成，`remove()` 两边同步删，新增 `restore()` 启动重放；`main.py` 启动日志加"定时任务恢复=N"
- **顺手修了一个真 bug**：rule 解析器 `_extract_frequency` 的时段词缺"早上/清晨/凌晨"、分钟不认"半"——"每天早上8点半"这类高频口语会**静默不注册定时**（cron=None 无任何提示）。已修＋8 用例单测全过（`每天早上8点半→30 8 * * *`、`每周一早上8点半→30 8 * * 1` 等）
- 文档：操作指南启动方式加"方式四：服务化常驻"，FAQ 端口占用条目改写；详设 2.5 持久化边界改写、目录树补 store.py 与 service/

- service 脚本全部补 UTF-8 BOM——Windows PowerShell 5.1 读无 BOM 文件按 GBK 解析，中文字符串直接语法崩溃（实测踩中：启动器秒退，报"字符串缺少终止符"）；5.1 与 pwsh 7 双兼容
